## 1. Findings that move money

Severity reads: **permissionless** = any address can trigger it;
**operator-scoped** = needs the admin key, and therefore falsifies a
"no-owner-drain" claim rather than being an open door.

### F1 — `ScrySilo` destroys its own emission stream, permissionlessly · HIGH

`ScryGardener.updatePool` carries the scaled remainder (`carryScaled`, added
2026-07-22) precisely because, without it, an interval where
`(reward · 1e12) / supply` floors to zero **advances `lastRewardTime` anyway** and
that second's emission is gone forever. `updatePool` is public, so anyone can
drive it.

**That fix was never ported to `ScrySilo.updateBin`** (`src/ScrySilo.sol:156-167`),
which is the same shape, also public, and has no carry.

```
test_F1_silo_per_second_updateBin_destroys_the_emission_stream
  patient arm (one update after 1000s) : accrues
  griefed arm (updateBin every second) : accrues 0
test_F1_control_gardener_carry_survives_the_same_grief   → Gardener is fine
```

The threshold is `totalWeighted > rewardPerSecond · 1e12`, i.e. ~2.78e27 weighted
units at the posted 240/day rate — **~2.8 billion sealed coins at 1×, or ~556M at
the 5× tier ceiling**, and it halves again for each bin sharing the alloc stream.
OBOL is uncapped and elastic; this is inside the reachable range, and the attack
costs a griefer only gas.

**Fix:** port `carryScaled` verbatim from `ScryGardener.sol:119-136`.

### F2 — `ScryGardener` LP donations permanently dilute every staker · MEDIUM

`updatePool` reads `p.lp.balanceOf(address(this))` as the staked supply
(`src/ScryGardener.sol:124`). LP tokens sent in by a plain `transfer` have no
`UserInfo` row, so they can never claim — but they **do** enlarge the denominator.

```
test_F2_gardener_lp_donation_dilutes_stakers_permanently
  sole staker with 100e18 staked, 900e18 donated, 1000s x 1e18/s emitted
  owed: 100e18 instead of 1000e18 — 90% stranded forever
```

This is the MasterChef-V1 bug MasterChefV2 fixed with an internal `lpSupply`.
Same fix here. (`ScrySilo` is immune: it tracks `totalWeighted` internally.)

### F3 — `ScryHarvest.sweep` can take money a live claimant is owed · MEDIUM-HIGH

`sweep` computes the outstanding obligation as `totalCommitted − totalClaimed`
(`src/ScryHarvest.sol:86`) — but `totalCommitted` describes the **current** root
while `totalClaimed` is the **lifetime** figure. The two only line up if every
root re-includes every wallet that has ever claimed. Nothing on-chain says so,
and nothing warns.

```
test_F3_harvest_sweep_can_take_a_live_claimants_money
  root1 = {A:100, B:50}, funded 150. A claims 100.
  operator re-posts root2 = {B:50}  (the natural "next epoch" root)
  owedMax = 50 − 100 → clamps to 0 → sweep(50) empties the contract
  B's still-valid, still-posted claim now reverts.
```

**This is the founding drop's contract.** `DeployClaim.s.sol` deploys one
`ScryHarvest` per token, and `LAUNCH-DECISIONS.md` leans on *republishable roots*
so nobody forfeits by being slow — republishing is exactly the operation that
arms this.

**Fix:** track `committedRemaining` explicitly (decrement on each `claim`, reset
on `postRoot`), or require `totalCommitted_ >= totalClaimed` in `postRoot`. Also
worth noting: `totalCommitted_` is **operator-asserted**, never derived from the
root — the contract cannot tell a wrong total from a right one.

### F4 — `ScryJobBoard.dispute()` lets the arbiter reenter and pay a job twice · HIGH (operator-scoped)

`dispute()` calls the arbiter **before** closing the job (`src/ScryJobBoard.sol:169-174`):
`flatFee()` → `transferFrom` → `rule()` → *then* `j.status = Closed`. `rule()` is
declared non-view on `IScryArbiter`, so it is a `CALL`, not a `STATICCALL`. While
it runs, the job is still `Delivered` and `close()` is open to anyone once the
deadline has passed.

```
test_F4_jobboard_dispute_reentrancy_pays_one_job_twice
  two 100e18 escrow jobs, 200e18 in one pooled balance
  job A past deadline, delivered; seller disputes
  the arbiter reenters close(A) from inside rule()
  → seller paid 190e18, splitter 10e18, board balance 0
  → buyer B's escrow is gone; their job can no longer settle or refund
```

### F4b — the arbiter also names its own fee and its own recipient · HIGH (operator-scoped)

`dispute()` pulls `arbiter.flatFee()` from the caller to `arbiter.feeRecipient()`
with **no ceiling and no sanity check**. The Insured / ReputationOnly flow asks
buyers for a standing approval so `_tryPull` can work.

```
test_F4b_..._unbounded_fee_against_the_callers_allowance
  buyer approves the board (as the flow requires), posts, disputes
  → 998e18 of the buyer's balance lands in the arbiter's pocket as a "flat fee"
```

**Both falsify the contract's own headline** — *"No owner-drain: job funds only
ever move along a job's own outcome"* (`src/ScryJobBoard.sol:36`). `setArbiter`
is a params-only knob in the comments and an arbitrary-code knob in fact.

**Fixes, both cheap:** (1) move `j.status = Status.Closed` **above** the arbiter
calls — plain checks-effects-interactions, and it kills F4 outright; (2) cap the
arbitration fee (a constructor-immutable `maxArbFee`, or read `flatFee()` once at
`post()` and pin it to the job); (3) drop the `// params only; never a fund path`
comment or make it true.

### F5 — `ScryGarden.addLiquidity` keeps the over-supplied side, with no refund · MEDIUM

Shares are priced off `min(...)` and there is **no router, no refund, no
`minOut`, and no deadline** anywhere in the contract.

```
test_F5_garden_addLiquidity_keeps_the_excess_with_no_refund
  pool at 1:1; LP adds 10e18 / 100e18 → 10e18 seeds, 90e18 token1 kept
```

On its own this is a play-money UX wart, and `ScryGarden`'s natspec says so:
*"⚠ … Never point real value at this."* The problem is that **`DeploySpoils.s.sol`
points real value at it** — on RH-Chain it defaults to building
`ScryGarden(OBOL, SCRY)` and `ScryGarden(MYRRH, SCRY)` against canonical SCRY.
Pick one: either the Garden is toy-only (and `DeploySpoils` should not pair it
with SCRY), or it holds real value (and it needs `minOut`/deadline/refund before
it does). Today the source file and the deploy script contradict each other.

*(Checked and clear: `ScryBurrow`'s manipulable-spot oracle is wired only to the
`DeployPlayground` PlayToken Garden, never to a SCRY one.)*

### F6 — `DeployGardener.s.sol`: the documented-optional env vars are mandatory, and the pool is the one the doc warns against · MEDIUM

Two defects in the script that deploys the farm.

**(i) `vm.envOr`'s fallback is evaluated eagerly.** Lines 54-57 read:

```solidity
SpoilsToken reward = SpoilsToken(vm.envOr("REWARD_TOKEN", vm.envAddress("MYRRH_TOKEN")));
IERC20 seed = IERC20(vm.envOr("SEED_MYRRH_SCRY_PRIMARY", vm.envAddress("SEED_OBOL_SCRY")));
```

Solidity evaluates arguments before the call, so `vm.envAddress(...)` runs
**always** — `MYRRH_TOKEN` and `SEED_OBOL_SCRY` are required even when the
primaries are set. The header comment calls the first "honoured as a fallback so
an older runbook still works"; it is not a fallback. The documented runbook
(`export SEED_MYRRH_SCRY=…`) reverts.
(`test_F6_envOr_fallback_is_eager_so_the_deploy_runbook_is_wrong`.)

**(ii) The header and the code disagree about which pool is farmed.** The comment
block argues at length that the farmed pool must be **MYRRH/SCRY**, because
paying OBOL to OBOL/SCRY LPs is the self-draining loop `FARMING.md` warns about.
Line 74 then adds `SEED_OBOL_SCRY` as **pid 0**, and the documented
`SEED_MYRRH_SCRY` becomes pid 1. The code does the thing the comment forbids.

This fails loudly (a revert, not a silent misdeploy), but it is on the Phase-1
keystone path and it is unreviewed by any test.

## 3. Lower-severity notes, by contract

**`ScryArbiter`** — `vote()` accepts any `jobId`, including ids that do not exist
yet on any board. A panel can pre-rule a future job; `dispute()` would then settle
instantly on a verdict cast before the evidence existed. Bind votes to a board
address, or require the board to open the case first.

**`ScryGranary`** — the daily cap keys on `block.timestamp / 1 days`, so a grantee
can spend a full cap at 23:59 and another at 00:01 (2× in two minutes). Standard
for daily caps; worth one sentence in `FARMING.md` since the cap is posted as the
emission throttle. Separately, `stewardMint` is deliberately uncapped — correct,
but it means the throttle binds grantees, not the steward.

**`ScryGardener` / `ScrySilo`** — `claimLocked()` / `claimOwed()` call
`granary.mint` **without** the `try/catch` that `_settle` uses. A revoked grant
makes them revert rather than defer. No principal is trapped (that was the rule's
point), but the behaviour is inconsistent with the stated "never bricks".
`setLockBps` also skips `massUpdate*`, so raising it retroactively locks accrual
earned under the old number.

**`ScryOrchard`** — `_max` is dead code. `uint160(secondsInsideX128)` truncates
silently for windows longer than ~2^32 seconds; a `require(endTime - startTime <=
type(uint32).max)` in `createIncentive` closes it for free.

**`ScrySteleEdition`** — `mintEdition(bytes32 vowId)` validates nothing. It has no
link to `ScryVowRegistry`, so anyone can mint an on-chain "print of a vow" for a
vow that does not exist and list it as genuine. Either check
`registry.tokenOf(vowId) != 0` or make the metadata say the print is unverified.

**`ScryDeed`** — `transferFrom` burns the toll from `msg.sender`, which on any
marketplace is the router, not the buyer. Routers hold no OBOL and grant no
allowance, so **deeds are effectively non-tradeable on OpenSea and every
aggregator** — which removes the "churn is the burn" sink the design is built
around. Disclosed in the natspec, but the consequence is not. Also: `found()`
accepts any `(streetIndex, plot)` in the full 16×16-bit space, so the "off-chain
scarcity knob" is unenforced on-chain and founding order can be front-run.

**`ScryBank`** — `leave()` divides by `totalSupply` before burning, so a call
before the first `enter()` panics with 0x12 rather than a message. Share-price
inflation can also make small deposits revert (`"amount too small for pool"`) —
a griefing DoS, priced high enough to be uneconomic. The `MINIMUM_SHARES` donation
guard itself checks out.

**`ScryVowRegistry` (LIVE)** — `setOracle` has no zero-check; one typo ends
anchoring forever, and there is no owner path to fix it (`oracle` is
self-rotating only). Worth a note in the runbook since the contract is already
broadcast. `balanceOf(address(0))` returns 0 where ERC-721 says revert — harmless
spec drift.

**`ScryPact`** — `parties[]` entries are not zero-checked (a pact with a zero
party can never reach `isActive`), and `roles[]` has no length bound while
`obligations[]` does.

**Checked and clean:** `SpoilsToken`, `ScryReputation`, `ScryNotary`,
`ScryCovenant`, `ScryShrine`, `ScryPeculium` + factory (the admission/rotation
logic is careful — malleability guarded, digests replay-consumed, epochs
monotone, ascending-verifier dedup, chain-id bound), `ScryEidolon` (the 52-byte
leaf really does close the second-preimage hole), `PlayToken`, `ScryBurrow`
(within its stated toy scope).

## 4. Cross-cutting

- **Zero invariant tests, two fuzz tests repo-wide.** Every numeric law is pinned
  at hand-picked points. F1 and F2 are both conservation properties an invariant
  test would have caught (`sum(user rewards) == emission over window`;
  `lpSupply == sum(UserInfo.amount)`).

- **`_b64` is duplicated verbatim** in `ScryDeed`, `ScryEidolon`,
  `ScrySteleEdition`, `ScryVowRegistry`. Bytecode cost, not a bug.
- **Merkle dialects agree.** `ScryHarvest._verify` (`h < p`) and

  and both match `ScryVowRegistry.verifyProof`. Leaves are 52 bytes and nodes 64,
  so no leaf can be forged as a node in any of them.

## 4b. F7 — Insured mode was free money for anyone willing to be both sides · CRITICAL

**Found by a parallel session's reproduction (`test/PoolDrain.t.sol`), not by
the read above — this audit missed it.** Recording that plainly, because the
miss is instructive: §3 noted that `ScryInsurancePool.claim` has no per-job
dedup and that the premium is unvalidated against `amount`, and stopped there
instead of asking who chooses the counterparty.

`post(…, Mode.Insured, …)` escrowed nothing, gated nothing, and priced the
premium against nothing. A buyer and seller controlled by one person could
post, deliver garbage (the board never checks `deliveredHash` against
`specHash`), let the deadline pass, and have the pool cover the "seller" in
full. **Measured: ten rounds of a ONE WEI premium took 9,500 SCRY out of a
10,000 SCRY pool**, with a fresh throwaway pair each round so the soulbound
rep slash landed on addresses nobody meant to reuse. And `_payoutSeller` called
`rep.earn` on the covered path, so draining the pool *built* the reputation
that any future gate would rely on.

**Fixed with three independent bounds**, because no one of them is sufficient:

1. **`post` in Insured mode now requires `rep.meets(seller)`** — the same bar
   ReputationOnly already demanded. Escrow risks the buyer's own money, so the
   board can be indifferent to who they are; Insured risks *other people's
   premiums*, so it cannot be.
2. **`minPremiumBps` (posted, capped at 50%, default 300)** — the premium is
   priced against the sum it may claim, so a round costs money proportional to
   what it can take.
3. **`ScryInsurancePool` caps what any ONE beneficiary draws per rolling
   window** (`windowCap`/`windowSeconds`, defaulting to one full claim cap per
   day). This is the bound that actually caps the loss: a per-*claim* cap
   bounds one payout and nothing else. Ten rounds in a day now pay the cap
   **once**, not ten times.
4. **A covered claim no longer earns rep.** It is not an honest completion —
   the counterparty defaulted and strangers paid. Cover makes the seller whole;
   it never also makes them more trusted.

**⚠ RESIDUAL RISK, and it is the operator's call, not a code fix.** These raise
the cost and cap the rate; they do not make self-dealing unprofitable in the
limit. Two reasons, both worth writing down before this mode is ever armed
against a pool with real size in it:

- **Mutual insurance against a counterparty you chose yourself is structurally
  exploitable.** Nothing on-chain distinguishes a real hire from one person
  wearing two addresses. The general fix is an underwriting step — someone
  accepts the specific risk — not a tighter parameter.
- **`ScryReputation` is not a Sybil barrier.** Escrow mode has no rep gate, a
  self-dealt escrow job costs only `feeBps` of the amount, and `amount` may be
  1 wei (where a 5% fee rounds to zero). So rep can be farmed to any threshold
  for gas. Bound 1 raises the attacker's setup cost from nothing to a few
  transactions — real, but not a wall.

**Recommendation: keep Insured mode's pool small and disclosed until an
underwriting step exists**, and treat `windowCap` as the real exposure limit.
Escrow and ReputationOnly are unaffected by any of this.

**And the §3 notes that were open because they were design changes — now
closed as code, not as notes:**

- **`ScryArbiter` is bound to ONE board, once** (`setBoard`, owner-only,
  never re-pointable) and refuses a vote on a `jobId` that board never issued.
  A panel could previously pre-rule a job that did not exist, and `dispute()`
  would settle on that verdict the instant the job was posted — decided before
  the evidence existed. `vote()` now reverts `"board not bound"` until wiring
  is done, which `DeployScryMarket.s.sol` attempts and loudly reports.
- **`ScrySteleEdition` checks the register.** `mintEdition` requires

  the flat price, because a print only good vows could buy would be a score
  money can move.
- **`ScryDeed`'s toll no longer makes deeds untradeable.** It burns from the
  **departing owner** when they hold OBOL and have approved this contract, and
  only otherwise from `msg.sender`. On OpenSea and every aggregator
  `msg.sender` is a router that holds no OBOL, so the old unconditional
  `msg.sender` toll silently made every deed non-tradeable off-site — killing
  the churn that IS the burn (`SENTENCES.md` 2026-07-22). `sellerCoversToll()`
  is the read a listing UI makes. ⚠ Escrow-and-list marketplaces are still not
  covered, and the natspec says so.
- **`ScryVowRegistry.setOracle`** — live, unpatchable, so it is now a standing
  hazard note with the exact `cast` sequence in `RUNBOOK.md` §4b.

## 8. Four copies of ERC-721, and what to do about it

`lib/` contains only `forge-std`. Every NFT here implements the standard by
hand, four separate times:

| contract | lines | live? |
|---|---|---|
| `ScryVowRegistry` | 388 | **LIVE** — unfixable, and it is the one that drifted worst (`balanceOf(address(0))` returns 0 where the spec says revert) |
| `ScryDeed` | 507 | unbroadcast |
| `ScrySteleEdition` | 375 | unbroadcast |
| `ScryEidolon` | 275 | unbroadcast |

Forking a reviewed implementation would have been the better call and the
drift is the proof: the ERC-4906 gap above, the `balanceOf(0)` divergence, and
`_b64` duplicated verbatim in three of them.

**But migrating now is the wrong trade.** The live one cannot move, so a
migration buys consistency across three contracts carrying 66 passing tests
between them, at the cost of a new dependency, three rewrites, and a fresh
audit surface — and it would not have prevented the HIGH finding above, which
lived in scry-specific toll logic that no ERC-721 base class has an opinion
about. The cheap durable answer is a **shared conformance suite** run against
all four, so drift is caught rather than rediscovered. Logged, not done.

**One thing genuinely still open, and it is a knob, not a defect:** when
Insured mode is eventually opened, `windowCap` and the pool's funded size are
the real exposure limit. Fund it with what you would shrug at.
